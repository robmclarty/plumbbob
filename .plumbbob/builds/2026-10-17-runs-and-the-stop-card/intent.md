# Runs and the stop card

**Phase** (your own bookkeeping while framing): plan authored from Rob's request at the plan prompt, with the verb's name and the end of a range settled there; Q1 to Q8 settled as their leans at the plan pause and in refine (2026-10-18), with one repair to step 11; awaiting approval
**Size:** medium
**Scope:** run

*Source: Rob's request at the plan prompt (2026-10-17), quoted whole under [Source](#source), with two calls he settled at the same prompt: the verb is `run` ([D1 (run-verb)](#d1)), and a run closes its range on a review card the model writes ([D8 (stop-card)](#d8)). It builds on the build-ranges build (`.plumbbob/builds/2026-10-17-build-ranges/`), released in 0.13.1. Every claim about plumbbob's code was read on `main` at 0.13.1 (`10c4b0e`), the baseline this build starts from, and the line numbers are from that commit.*

## Frame

- **Problem:** The card names the range to type beneath Next Up (`· range 3 of 5: /plumbbob:build 6-9`), and the human copies its step numbers back into a prompt at every stop. Those numbers are the plan's to know, and they move: a run that stops early leaves fewer of them, the build order can put an appended step inside a range, and a refine re-cuts one. Nothing lets the human say "run the next range" or "run range 3" and have plumbbob work out the rest. The stop itself is thin. A range that lands its steps stops for a review (plumbbob [D92 (build-ranges)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d92)), but the run's turn ends on its last step's checkpoint block: every step before it landed without a pause, so a step that landed a hair off mid-range never reaches the screen, and the parks the range piled up sit behind a count at the end of the note (`parked 4 of 7 open`). Harvesting them is a separate command with a confirmation per item, and checkride's polyglot build parked 64 items over its run.
- **Smallest thing that solves it:** a `/plumbbob:run` verb that runs what is left of the range holding the next step, or of range N, with its grant minted by the turn hook from the plan at the keystroke; the card and the dashboard naming it; and a stop card that closes a run's range: the model's account of the whole range, the CLI's readout across its steps, and every open park with a proposed class, settled in one reply and recorded by a latched `plumbbob harvest`.
- **Done looks like:** in a throwaway repo whose plan declares ranges, `/plumbbob:run` lands exactly the range holding the next step and ends on its stop card, and `/plumbbob:run 3` runs range 3; every card that named `/plumbbob:build 6-9` names the run instead; `looks good` at the stop card records the harvest and the range's review in the build log, and `plumbbob harvest` refuses in the card's own turn; a plan without ranges, and `/plumbbob:build` in every form, behave exactly as they do today; c11 holds the run to its range in a targeted run; and `pnpm check` is green.
- **Explicitly NOT doing:** chaining ranges (`/plumbbob:run 2-4`, or `--auto` on a run); a run nobody typed, so `looks good` never starts one (plumbbob [D65 (human-typed-grants)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d65)); the CLI deciding where a range stops; a `plumbbob run` CLI verb, since the CLI resolves and records while the skill builds; a new grammar for the plan's section; a stop card for a range landed by `/plumbbob:build`, a typed range, `--auto`, or by hand; a rendered card for a harvest outside a stop; editing another build's record, here or in another repo; a version bump or CHANGELOG entry.

## Decisions

- <a id="d1"></a>**D1 (run-verb)**: the verb is `/plumbbob:run`, settled at the plan prompt, *because* it is a verb for a command that does something, it is the word Rob reached for ("build run 3"), and it splits the act from the plan's noun: the plan declares ranges, and a run is one range being built; Claude Code ships a `/run` skill of its own, so a bare `/run` reaches theirs, the same accepted collision as `/plan`, `/status`, `/doctor`, and `/verify`.
- <a id="d2"></a>**D2 (run-names-a-range)**: `/plumbbob:run` names the range holding the next undone step in build order, the step in flight counted undone, and `/plumbbob:run N` names range N by its item number; either runs what is left of that range, written in build order, *because* that is the range and the command the card already names (plumbbob [D93 (range-on-the-card)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d93)), and the item number is the handle the card counts by.
- <a id="d3"></a>**D3 (plan-names-the-grant)**: the turn hook mints a run's grant from the plan as it stands when the human types the verb, `steps <what is left>` for a range that lands its steps and nothing for a bare range, which builds to its pause; the set is frozen at the keystroke like a typed list (plumbbob [D91 (step-list-grants)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d91)), and a range on its own still grants nothing, *because* the human types the verb against a card that names that range and its steps, a frozen set cannot widen with a later edit to the ranges or the build order, and reading the committed plan instead would disagree with the card after any re-cut at a boundary; it amends plumbbob [D92 (build-ranges)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d92)'s "a range grants nothing".
- <a id="d4"></a>**D4 (namespaced-run)**: only the namespaced `/plumbbob:run` mints, and it reads the one token after it: a range number names that range, a token carrying a dash or a comma mints nothing, and anything else names the next range, *because* a bare `/run` reaches Claude Code's own skill and must leave no grant behind, and a span of ranges (`2-4`) is a form this build does not define, so it must not be read as another today.
- <a id="d5"></a>**D5 (run-refuses)**: a run that names nothing it can walk mints nothing and refuses with the move that unblocks it: a plan without ranges (`/plumbbob:refine ranges`, or `/plumbbob:build` for the next step), a step no range names or a flagged range (its drift words, then `/plumbbob:refine ranges`), a landed range or a number no range carries (the range the card names), and nothing left (`/plumbbob:finish`), *because* a run's promise is the plan's stops, so a run with no range would have no stop or be a single step, and a guessed range is the early halt ranges exist to remove.
- <a id="d6"></a>**D6 (one-loop)**: the run skill carries only what is the run's own (resolving it, refusing, the stop card, and the reply to it) and reads the build skill beside it, `../build/SKILL.md` from its own base directory, for the per-step loop, and the harvest skill the same way for the classes and the fold rules, *because* two copies of the loop would drift apart, the build skill is the engine both verbs drive, and c11 measures whether the read holds.
- <a id="d7"></a>**D7 (card-names-the-run)**: the range segment names `/plumbbob:run` where it named the range's explicit command, with the steps it lands beside it, and so does the dashboard's `next →`; the plan's section keeps the explicit command as the range's definition, *because* the run is what the human types now and the steps are what it will land, and every plan written since plumbbob [D92 (build-ranges)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d92) keeps parsing; it amends plumbbob [D93 (range-on-the-card)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d93).
- <a id="d8"></a>**D8 (stop-card)**: a run that lands its range ends on the stop card, a decision turn the model writes into the detail file and `plumbbob handoff --stop` renders: the Stop lead, a summary and highlights of the whole range, the range's readout and Verdict, every open park with a proposed class, Next Up, Your Call, and the recommendation; a range landed by `/plumbbob:build`, a typed range, `--auto`, or by hand keeps today's boundary, *because* a landing range's stop is a review, and today a run's review has nothing to read but the last step's block while the parks pile up behind a count (settled at the plan prompt); it amends plumbbob [D85 (range-top-lands)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d85): a run's clean halt lands its top step first, then ends on the stop card rather than the checkpoint's block.
- <a id="d9"></a>**D9 (range-readout)**: the stop card's readout is measured by the CLI across the range, from the steps' commits and `stats.json` (the steps it landed, the check across its landings, each step's commit against its own seam, the diff summed, and the time spent), while the done-when, decisions, and constraints rows are the model's, and the Verdict folds them all worst-of, *because* the CLI measures whatever it can (plumbbob [D80 (cli-renders-model-relays)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d80)) and a landed range's facts are already on record.
- <a id="d10"></a>**D10 (settle-in-one-reply)**: the stop card's proposals are settled in one reply: `looks good` confirms every one, a reply that changes one is direction (the card re-renders with it changed, and nothing is recorded until `looks good`), and `/plumbbob:run` typed at the card confirms them all and runs the next range; each park carries a handle the card prints, distinct from the highlights' numbers, *because* the human reads every proposal on the card, one reply per item is what makes a stop's harvest a chore, and the classes stay the human's call, which is the harvest skill's contract.
- <a id="d11"></a>**D11 (stop-latched)**: the stop's record is latched: `plumbbob harvest` refuses in the turn the stop card printed, and refuses a range's detail that no stop card showed, *because* a run's long turn that ends on proposals is where a model would carry straight on into recording its own, and the record is where plumbbob holds the line (plumbbob [D64 (approval-latch)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d64)).
- <a id="d12"></a>**D12 (harvest-records)**: `plumbbob harvest` records a harvest from the detail file: it flips each settled park, appends the dated Harvest lines, and at a stop writes the range's review beneath a dated Log line; the `/plumbbob:harvest` skill records through it too, *because* everywhere else in plumbbob a skill decides and the CLI records, and a range's review is the record a PR reviewer reads, kept the way `checkpoint` keeps a step's pause beneath its Log line.
- <a id="d13"></a>**D13 (run-at-a-pause)**: typed while a step waits at its pause, `/plumbbob:run` is that pause's `looks good`, so it lands the step only on a green check, followed by what is left of the range holding the step; the run ends where that range does, so a bare range's run ends once its step lands, and a landing range's ends on its stop card even when the paused step was its last; the pause card offers the move only inside a landing range, where it does more than `looks good`, *because* finishing the run that holds the next step is the verb's promise, approving the paused step is its first beat, and a run that halted on trouble would otherwise take two replies to resume (settles [Q1 (run-at-a-pause)](#q1)).
- <a id="d14"></a>**D14 (stop-record)**: recording a stop commits nothing, and the range's review and the harvest ride the next step's checkpoint, or the finish, as a harvest's edits do today, *because* a stop commit needs a fourth kind of ledger line that `recover`, `revert`, `status`'s out-of-band count, and the finish report would each have to learn, while the Log already carries the review to the PR (settles [Q2 (stop-record)](#q2)).
- <a id="d15"></a>**D15 (empty-stop)**: a run whose range lands with no park open still ends on the stop card, rendered without its Harvest part, and `/plumbbob:run` typed at it records the review and runs the next range, *because* the review is the stop's point, the plain block leaves it nothing to read, and the only reply the card costs is the next run the human was going to type anyway (settles [Q3 (empty-stop)](#q3)).
- <a id="d16"></a>**D16 (stop-card-held)**: the hook marks a run in a `RUN` control file naming its range, written beside `GRANT` and cleared by the next typed prompt unless a step of that range waits at a pause, while a notice leaves it as it leaves `GRANT`, and the latch reads grants exactly as it does now; the checkpoint that completes a marked range writes its `RELAY` record as owing the stop card, and the relay check holds a turn whose last ending still owes it, once (plumbbob [D89 (block-once)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d89)), with `plumbbob handoff --stop` as the retry, *because* only the run skill's prose asks for the card's second beat, a boundary relayed whole passes the check today, and a new clean-halt shape has gone wrong under the eval tier before, in 2 of 4 runs (plumbbob [D85 (range-top-lands)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d85)); the mark outlives a prompt at a pause inside its range so that a halt approved with `looks good` still owes the card (settles [Q4 (stop-card-held)](#q4)).
- <a id="d17"></a>**D17 (live-run-early)**: step 6 runs one headless session in a throwaway repo, with this checkout loaded as the plugin and the grant pre-armed the way c4 arms it, that lands a two-step range through `/plumbbob:run`; range 2 spends that one session, and its stop reads the result before step 7 builds on the skill, *because* the run skill's read of the build skill ([D6 (one-loop)](#d6)) is the build's one untested bet on model behavior, and finding it broken at step 14 would mean a redesign beneath steps 7 to 13; the build-ranges build ran its one live plan session inside a range the same way (settles [Q5 (live-run-early)](#q5)).
- <a id="d18"></a>**D18 (fold-then-run)**: `/plumbbob:run` typed at a waiting stop card records the stop first, and when `status --run` then reports the grant unlike the run, because the harvest added or moved a step in the range it would walk, the run ends at the boundary, where the card names the re-cut run, rather than walking a grant that no longer covers the range, *because* the hook minted the grant from the plan before the record ran, and halting before a step its own harvest added is the early halt [D5 (run-refuses)](#d5) says ranges exist to remove; it refines [D10 (settle-in-one-reply)](#d10) (settles [Q6 (fold-then-run)](#q6)).
- <a id="d19"></a>**D19 (in-flight-first)**: a step in flight decides the run: `/plumbbob:run` names the range holding it, `/plumbbob:run N` naming another range refuses, and so does any run while a spike is open, each with the dashboard's remedy (`/plumbbob:verify` or `/plumbbob:abandon` the step, or `plumbbob spike done`), and the hook mints nothing for a refusal, *because* a run that starts elsewhere rewrites the step markers, and its first checkpoint stages the step in flight's half-built diff into another step's commit, while a spike is an unresolved fork a run would build on; it amends [D2 (run-names-a-range)](#d2) and [D5 (run-refuses)](#d5) (settles [Q7 (in-flight-first)](#q7)).
- <a id="d20"></a>**D20 (finish-at-a-stop)**: the finish skill records a waiting stop card the way `looks good` would, through `plumbbob harvest`, before it writes the report, and the last range's card names `/plumbbob:finish` in its Your Call as that move, *because* every build whose plan declares ranges ends its last run on a stop card, finish is the move after it, and a review the finish skips never reaches the Log or the report (settles [Q8 (finish-at-a-stop)](#q8)).

## Constraints

- <a id="c1"></a>**C1 (no-new-deps)**: no new dependency of any kind.
- <a id="c2"></a>**C2 (hooks-never-wedge)**: every hook path (`turn`, `relay`) still exits 0 and degrades to no output on any failure, and a run's grant degrades to none.
- <a id="c3"></a>**C3 (records-stay-put)**: no file in another build's folder is edited, here or in another repo; every plan written since plumbbob [D92 (build-ranges)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d92) keeps parsing, its explicit range commands included.
- <a id="c4"></a>**C4 (spec-first)**: a change to a turn's shape lands in `docs/presentation.md` before the code that renders it, per plumbbob [D80 (cli-renders-model-relays)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d80).
- <a id="c5"></a>**C5 (no-release)**: no version bump and no CHANGELOG entry; the release is cut by hand with `/version`.
- <a id="c6"></a>**C6 (temp-repo-dogfood)**: hand-run checks use `node src/cli.ts` in a `mktemp -d` repo, never a stale `dist/` and never this repo's live session.
- <a id="c7"></a>**C7 (house-voice)**: authored prose follows `docs/voice/` with no em-dash (plumbbob [D78 (em-dash-ban)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d78)), relayed CLI strings keep theirs, and every citation carries its slug (plumbbob [D74 (glossed-citations)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d74)).
- <a id="c8"></a>**C8 (old-grants-land)**: the latch keeps honoring `range M` and `steps` grants exactly as it does, *because* this repo's own hook is the installed 0.12.1 plugin's until a release, and this build's ranges are typed as `/plumbbob:build N-M` under it.
- <a id="c9"></a>**C9 (numbers-for-life)**: nothing renumbers a step or a range, and a run names a range by the item number the plan gave it (plumbbob [D86 (build-order)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d86)).
- <a id="c10"></a>**C10 (build-unchanged)**: `/plumbbob:build` behaves as it does today: a bare build ends at its pause, a typed range and `--auto` end as plumbbob [D85 (range-top-lands)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d85) and [D94 (auto-and-stops)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d94) say, and contracts c1 to c10 pass unchanged.

## Build ranges

Six commands drive the build, in the grammar plumbbob [D92 (build-ranges)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d92) settled. Three stops are calls made at a step's own pause (the run's strings at step 1, the stop card's at step 7, and the eval's result at step 14), and three are reviews after a range lands, the last of them also the call to spend the eval's live sessions. Range 2 spends one live session at step 6 ([D17 (live-run-early)](#d17)), small enough to ride inside it. This repo's hook is the installed 0.12.1 plugin's, so every range is typed with `/plumbbob:build` until a release carries the run ([C8 (old-grants-land)](#c8)).

## Open questions

- <a id="q1"></a>**Q1 (run-at-a-pause)**: *resolved:* 2026-10-18, the lean, recorded as [D13 (run-at-a-pause)](#d13); the question was whether `/plumbbob:run`, typed while a step waits at its pause, approves that step
  - *plain:* A run that halts on trouble (a red check, a self-review mismatch) leaves its step at a pause, and a bare range ends at its own pause by design. Today the human answers `looks good`, the step lands, and the card names what is left of the range for the next prompt: two messages. Reading `/plumbbob:run` at a pause as the approval saves one, but the verb would then do two things depending on where the build stands, and an approval would ride a command the human may type out of habit. The latch allows it either way, since the prompt is a human turn and the step in flight may land (plumbbob [D64 (approval-latch)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d64)).
  - *lean:* yes: at a step's pause, `/plumbbob:run` is that pause's `looks good`, so it lands the step only on a green check, followed by what is left of the range holding it; the run ends where that range does, so a bare range's run ends once its step lands, and a landing range's ends on its stop card, even when the paused step was its last. The pause card offers it as a move only inside a landing range, where it does more than `looks good`, and step 1 words the segment at a pause so the card never names a range the run would not reach.
- <a id="q2"></a>**Q2 (stop-record)**: *resolved:* 2026-10-18, the lean, recorded as [D14 (stop-record)](#d14); the question was whether recording a stop commits anything
  - *plain:* `plumbbob harvest` writes the range's review and the harvest into `build-log.md`, and a confirmed blocker folds into `intent.md`; both are tracked. A commit of its own, like the plan commit, would keep those edits out of the next step's diff and put the review in `git log`, but the checkpoints ledger reads three kinds of line (`baseline`, `plan`, `step N`), and `recover`, `revert`, `status`'s out-of-band count, and the finish report all read the ledger, so a stop commit needs a fourth kind each of them learns, or it shows as an out-of-band commit on every dashboard.
  - *lean:* no commit: the record rides the next step's checkpoint, or the finish, as a harvest's edits do today. The Log is where a PR reviewer reads the review, and the ledger keeps its three kinds.
- <a id="q3"></a>**Q3 (empty-stop)**: *resolved:* 2026-10-18, the lean, recorded as [D15 (empty-stop)](#d15); the question was whether a run whose range lands with no park open still ends on the stop card
  - *plain:* The stop card does two jobs, the range's review and the harvest. With nothing parked, `looks good` records only the review, and the human spends a reply on it before typing the next run. Ending on the plain checkpoint block there instead saves the reply, but leaves the review stop with nothing to read but the last step's block, the gap the card exists to close.
  - *lean:* yes: the card renders without its Harvest part, and `/plumbbob:run` typed at it records the review and runs the next range, so the only reply it costs is the one the human was going to type anyway.
- <a id="q4"></a>**Q4 (stop-card-held)**: *resolved:* 2026-10-18, the lean, recorded as [D16 (stop-card-held)](#d16), with the mark kept across a pause inside its range; the question was what holds a run that ends on its last checkpoint's block instead of the stop card
  - *plain:* The stop card is a two-beat ending: the top step lands, then the model writes the range's detail and runs `plumbbob handoff --stop` ([D8 (stop-card)](#d8)). Only the run skill's prose asks for the second beat. A model that relays the last checkpoint's block instead passes the relay check, since that block is the last ending the CLI printed (`RELAY`) and a boundary relayed whole reads as a turn closed correctly, so the review and the harvest never reach the screen. A new clean-halt shape has gone wrong under the eval tier before, in 2 of 4 runs (plumbbob [D85 (range-top-lands)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d85)), and nothing in the CLI can tell a run's grant from a typed list's, since both mint `steps 6-9`.
  - *lean:* the hook marks a run in a `RUN` control file naming the range, written and cleared beside `GRANT`, so the latch reads grants exactly as it does now; the checkpoint that completes that range writes its `RELAY` record as owing the stop card, and the relay check holds a turn whose last ending still owes it, once (plumbbob [D89 (block-once)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d89)), with `plumbbob handoff --stop` as the retry. Steps 3 and 9 each gain a clause (step 9's seam gains `src/verbs/checkpoint.ts`), and step 14 arms the mark the way c4 arms the grant.
- <a id="q5"></a>**Q5 (live-run-early)**: *resolved:* 2026-10-18, the lean, recorded as [D17 (live-run-early)](#d17); the question was whether step 6 measures the run skill's read of the build skill in one live session, rather than leaving it to step 14
  - *plain:* The run skill leans on the model reading `../build/SKILL.md` for the whole per-step loop ([D6 (one-loop)](#d6)): the pause, the detail file, the checkpoint body, and the halts. No step before 14 runs a live session, so a model that skips the read, or takes the build skill's invocation rule for the run's, shows up only after steps 7 to 13 have built the stop card on top of it. A live session is spending, which the build ranges put behind a stop (plumbbob [D92 (build-ranges)](https://github.com/robmclarty/plumbbob/blob/main/docs/decisions.md#d92)), though the build-ranges build ran its one live plan session inside a range.

- <a id="q6"></a>**Q6 (fold-then-run)**: *resolved:* 2026-10-18, the lean, recorded as [D18 (fold-then-run)](#d18); the question was what `/plumbbob:run`, typed at a waiting stop card, does when the harvest it confirms adds or moves a step in the range it would walk

## Noticed, not in this build

- A harvest outside a stop could render a card of its own through `handoff`, the stop card without its range parts, so every harvest ends on a CLI-rendered Your Call.
- `finish`'s report could gather the ranges' reviews from the Log: what each range landed, and where one stopped early. The build-ranges build deferred the same table.
- A stop's markdown link prints raw on the dashboard (a tangent the build-ranges build deferred), and the run header prints the stop too.
- `order`'s ending could carry an advisory when the new sequence breaks a range, rather than the order skill writing one line ahead of it.
- `abandon`'s refusal still says "past the range you granted" for a list grant (`src/verbs/abandon.ts:109`), and a run's grant is a list.
- A span of ranges (`/plumbbob:run 2-4`) could run them back to back, halting at each bare range; [D4 (namespaced-run)](#d4) keeps the form unread until it is designed.

## Source

The request this build was planned from, as Rob typed it at the plan prompt on 2026-10-17. It is quoted rather than fenced, the same as every source this repo keeps under a plan, and its two command forms sit in code spans so a renderer keeps their `<...>` rather than reading them as tags.

> i want to push the range feature and make it a main verb. building on the last ranges build, i'd like a new verb that works alongside `build`. work with me to decide on the name: "range", "build_range", "run"... the intent is that like "build", this new verb kicks off the next upcoming build range run by number/index. it should work off the build order so that no matter what actual step we're on, if the user types "`/plumbbob:<whatever-the-name>`" the build will execute the current matching range that contains the next step. it works with the orders we just added so a "range step" may in fact be something like "70, 1-3, 5". the user can explicitly trigger a specific range like "`/plumbbob:<name> 3`" to trigger build run 3, or with no argument, it triggers the next matching run (or finishing the run containing the next step). this maybe become the primary way people use plumbbob where the existing "build" verb is only used for more granular step by step work, only when a range/run is not sufficient, or too risky to build at once. but for the most part, users will want the most bang for their buck. perhaps the ending of a range should be optimized for this use-case. it usually accumulates a lot of parked items that should be addressed. that process should be made more obvious.

The two calls settled at the same prompt, by Rob's picks: the verb's name is `run` (of `run`, `range`, and `build_range`), and the end of a range is a review card the model writes, with every open park and a proposed class (of that, a stop the CLI renders with the parks listed, and a pointer at harvest alone).
